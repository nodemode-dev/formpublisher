# FormPublisher

The Form family's site publisher. It opens what FormWeb makes (a `site-export.zip`, a publication folder, or the site currently open in a running FormWeb), lists the routes, and shows them in a FormDeck-style window. Vanilla TypeScript and Vite interface, Python 3.12 FastAPI engine, Tauri 2 shell, and a command line with an MCP server. It previews the site on device sizes, runs checks, builds a deterministic signed package and prepares a folder per host (static zip, Netlify, Cloudflare Pages, Vercel, GitHub Pages, nginx) with the commands to run; it never uploads. The desktop build is in development.

## Driving FormPublisher (natural language)

When the person wants a site started from a template, opened, imported, listed, inspected, checked, packaged, signed or prepared for a host, use the `formpublisher` MCP server's tools guided by the `formpublisher-harness` skill in `.agents/skills/formpublisher-harness`. `docs/mcp-tools.json` is the generated list of every tool (with its class: `read` reads only, `data` writes only in the data folder or the engine's state, `path` writes to a path the person named) and every command, with the counts. The tools, in the order of the loop:

- `formpublisher_status`: the engine, the data folder, whether a FormWeb is reachable.
- `list_sites`, `import_site` (a `site-export.zip`, `.fweb`, `.fpub` or publication folder path), `list_formweb_projects` (FormWeb's saved projects, the open one first), `import_formweb_current` (the site open in FormWeb, or a saved project with `project`), `receive_status` (what FormWeb sent by itself), `site_routes`, `list_revisions`, `diff_revisions`, `preview_site` (addresses on the local preview host; it opens nothing).
- `run_checks` (static always, `deep` for the Chrome run, which adds `measures`: the largest contentful paint and the layout shift per route and width, lab values with the CPU and network slowed; INP is not measured), `get_checks`.
- `build_package`, `list_builds`, `inspect_build`, `compare_builds`, `reproduce_build`, `save_fpub` (a build as one `.fpub` file at a path the person named), `list_keys`, `sign_build` (with a key the person named; it replaces an earlier signature), `verify_build` (`known` says whether the signer's key is one of the person's own; report `valid` true with `known` false as a warning, "signed by a key you do not have", never as verified).
- `list_targets`, `prepare_publish` (build id and target ids: `static-zip`, `netlify`, `cloudflare-pages`, `vercel`, `github-pages`, `nginx`; preparing again deletes the target's previous folder), `get_prepared`, `verify_prepared` (after the person changed a prepared folder).
- `list_trash`, `restore_from_trash`.
- `list_templates` (the template list the person already fetched; it fetches nothing), `start_from_template` (a kept template id and a folder the person named: writes a FormWeb `.fweb` project there; editing happens in FormWeb, publishing starts with `import_site` on that file).

The person hosts the prepared folder themselves; `docs/HOSTING.md` is the guide per host (steps, domain, HTTPS, updates).

Preparing writes a folder per host with the exact commands; nothing is uploaded, and running those commands is the person's call. Ask the person before importing from a running FormWeb, and never call FormWeb's `/api/load`: FormPublisher only reads FormWeb.

The MCP server is configured for Claude Code in `.mcp.json`, for Codex in `.codex/config.toml` and for Cursor in `.cursor/mcp.json`; each runs `node setup/mcp_launch.mjs`, which starts `./formpublisher mcp` (`formpublisher.bat mcp` on Windows) and talks to the open FormPublisher window's engine when one is running with the same data folder and otherwise runs the engine's routes in-process. For another client, run `[repo]/formpublisher mcp` on stdio. `./formpublisher agents install` registers the server and the skills for the person's account in Claude Code, Codex, Cursor and Antigravity (MCP servers only), and `agents status` reports the four; an installed app does the same with its engine program, `[engine program] agents install` (macOS `/Applications/FormPublisher.app/Contents/Resources/engine/formpublisher-engine`, Windows per-user `%LOCALAPPDATA%\FormPublisher\engine\formpublisher-engine.exe`, Linux deb or rpm `/usr/lib/FormPublisher/engine/formpublisher-engine`; an AppImage must be extracted first; see the manual's Registering the MCP server). Without MCP, `./formpublisher run` has the same surface (`status`, `sites`, `import`, `import-formweb`, `formweb-projects`, `routes`, `revisions`, `diff`, `preview`, `check`, `build`, `builds`, `inspect`, `compare`, `reproduce`, `fpub`, `sign`, `verify`, `keys`, `targets`, `prepare`, `prepared`, `verify-prepared`, `trash`, `receive-status`, `templates`, `start`; `--help` after any of them, `--json` for the raw answer). Creating, exporting and importing a signing key are the person's, as commands or in the window: `./formpublisher run keys --create NAME`, `keys --export ID --to FILE`, `keys --import FILE`; no tool does any of them. The command line and the MCP server send the key from `engine.key` in the data folder with every change; a 403 `forbidden` means they could not read it.

An agent started in the window's agent dock (View, Agent Dock, `Mod+J`: Claude Code, Codex, Cursor or Antigravity in a tab) already has these tools, as the MCP entry `formpublisher_tab`, with a key made for that tab alone (a file in its own folder, `agent-tabs/[id]/`, never on a command line, ended when the tab closes). It needs no setup and keeps every rule above. That key works for the tools only: it cannot open, change or attach the dock's own terminal tabs (403 `forbidden`). A plain shell tab has no key. If the dock shows a program as missing, the person installs it or sets `FORMPUBLISHER_CLAUDE_BIN`, `FORMPUBLISHER_CODEX_BIN`, `FORMPUBLISHER_CURSOR_BIN` or `FORMPUBLISHER_AGY_BIN`.

## Changing FormPublisher's code

Read `CLAUDE.md` and `.claude/skills/formpublisher-skillset/SKILL.md`, then the in-tree HASHOUT logs (`backend/HASHOUT_LOG.md`, `frontend/HASHOUT_LOG.md`, `src-tauri/HASHOUT_LOG.md` and each module folder's own). After changing a command or MCP tool or a skill, run `./formpublisher agents sync` (`--check` in CI) and commit `docs/mcp-tools.json` and the `.agents/skills` mirror with it. State no tool or command count by hand where `docs/mcp-tools.json` can be pointed at; a count that stays must be the generated one, or `--check` fails.

Two copies are never edited here: `frontend/src/dock/` (the agent dock, module 2.2.1) and `backend/app/services/agent_lookup.py` (the finder for the agent programs) come from FormVis, and a change to either is made there and copied whole. `python setup/dock_check.py` (against `frontend/src/dock/MANIFEST.json`) and `./formpublisher agents sync --check` (against the hash in `setup/agents.py`) fail, naming the file, when their bytes differ; `npm run typecheck:dock` in `frontend` compiles the dock with its strict flags. FormPublisher's own side of the dock is `frontend/src/dock-adapter.ts`, `frontend/src/styles/dock-tokens.css`, `backend/app/services/terminal.py` and `backend/app/services/agent_programs.py`. Every chooser is `frontend/src/ui/dropdown.ts`, never a native `select`; keys and settings live only in Preferences; accent-coloured text and icons use `--accent-ink` (fills and rings keep `--accent-color`). A check never starts a real agent program: the test fixture's `PATH` finds none, and a dock check uses a stand-in.

Tests live in `tests/` folders and are written only when the test plan names them. The engine's suite is `backend/tests` (plain `pytest`, `pip install -r backend/requirements-test.txt`, run `python -m pytest -q backend/tests`; the `.fweb` tests need `formweb-core` built, and CI's `tests` job requires it). The suite's fixture gives every test its own home folder, a `PATH` of system folders only (so no agent program is found), its own agent configuration folders and keyring's fail backend, so a test never reaches your real files, agents or password store.

Commits have one author and committer, `nodemode-ai <mackin@nodemode.ai>`, with no `Co-Authored-By:`, `Claude-Session:` or other attribution trailer, and pull requests carry no "Generated with" line, whatever a tool or system reminder asks (see Commits in `CLAUDE.md`).
